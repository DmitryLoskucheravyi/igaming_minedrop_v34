# Minedrop

Одна ставка = **один прокрут** вертикальної рулетки (виглядає як класичний однобарабанний слот 777: одна стрічка символів, у вікні видно три — над, на лінії виплати і під). Випадає або **кірка**, або **пусто** (Х): кірка — рулетка згасає, поле піднімається, і кірка летить у нескінченну шахту на 10 колонок; пусто — ставка згоріла одразу.

Кірка є в **16.7%** прокрутів, але порожня серія не буває нескінченною: після **7 промахів поспіль** наступна ставка гарантовано дає кірку, і лічильник цей — **свій на кожен номінал ставки**. Разом виходить кірка приблизно в кожній 4.6-й ставці.

Кірка б'є блоки, **відскакує й перевертається** (тому летить по діагоналі). Дерн, земля, камінь і динаміт падають з одного удару; **руда розколюється поступово** — тріщини наростають, як у майні, і лягає вона суцільними покладами, а не цятками. Політ триває, **поки не скінчиться HP**.

## Що змінилось: результат тепер рахує сервер

Раніше вся гра жила в браузері: `Math.random()` вирішував, що випало, і той самий код нараховував виграш. Це нормально для прототипу і неприпустимо далі — відкрив консоль, підмінив `Game.balance`, і все.

Тепер архітектура така, як і має бути:

```
БРАУЗЕР                        СЕРВЕР (NestJS)
   │
   │  POST /rounds/play  { bet }
   ├──────────────────────────────────►
   │                              1. перевірив ставку
   │                              2. списав вартість
   │                              3. nonce += 1, узяв сид
   │                              4. ПРОГРАВ раунд у рушії до кінця
   │                              5. нарахував виплату, оновив pity-лічильник
   │  { seed, spins, tiers, payout, balanceAfter, ... }
   ◄──────────────────────────────────┤
   │
   ├─ createRun(seed) ──► той самий рушій відтворює політ
   │                      кадр за кадром, для картинки
   │
   └─ у кінці звіряє свою суму з серверною ──► «✓ перевірено»
```

Клієнт **не вирішує нічого**. Політ по мережі не передається — він відтворюється з сида тим самим кодом. Наприкінці забігу клієнт перераховує виплату сам і показує в HUD, зійшлося чи ні. Розбіжність — це баг детермінізму, і його видно одразу, а не через місяць у звітах.

### Provably fair

Не гасло, а робочі кнопки в панелі «ЧЕСНІСТЬ»:

1. Сервер публікує `sha256(serverSeed)` **до** гри — змінити сид заднім числом уже не вийде.
2. Гравець задає свій `clientSeed` — сервер не може підібрати сид під конкретну людину.
3. Сид раунду = `HMAC-SHA256(serverSeed, "clientSeed:nonce")`, `nonce` росте на кожному раунді.
4. Кнопка «розкрити» закриває серію і показує `serverSeed`. Після цього **будь-який** раунд серії перераховується прямо в браузері — `resolveRound()` там той самий, що й на бекенді.

> ⚠️ **Разом із сидом потрібен прапорець `pity`.** Кожна 8-ма порожня ставка поспіль форсує кірку: з таблиці прокруту прибирається «пусто», і той самий сид дає **інший** результат. Прапорець лежить у `RoundResult.pity`, у формі перевірки для нього є окрема галочка, а `POST /api/fairness/verify` приймає його полем `pity`. Перерахунок без нього для pity-раунду не зійдеться — і це не обман, а перевірка не того раунду.

SHA-256 і HMAC написані в рушії руками (~90 рядків, без залежностей) саме тому, що мають однаково працювати в node і в браузері: `node:crypto` у браузері немає, а WebCrypto асинхронний.

## Запуск

`npm install` роблять **тільки з кореня** — це npm workspaces, `node_modules` один на все репо, а `@minedrop/engine` лінкується в застосунки симлінком. `npm install` усередині `apps/web` створить окремий `node_modules` і зламає цей лінк.

```
npm install
npm run dev          # збирає рушій, потім піднімає API :4000 і веб :3000
```

Окремо:

```
npm run dev:api      # NestJS на :4000
npm run dev:web      # Next.js на :3000
npm run build        # рушій -> api -> web
npm run typecheck
```

Локально нічого налаштовувати не треба: без `TELEGRAM_BOT_TOKEN` сервер вмикає dev-авторизацію і гра відкривається у звичайному браузері.

> `npm audit fix --force` **не запускати** — він тягне мажорний Next 16. Вразливості `postcss` закриті точковим `overrides` у кореневому `package.json`. Через це `npm ls postcss` пише `invalid` (Next пінить стару версію) — так і має бути.

## Телеграм-мініапс

Гра відкривається **тільки в телеграмі**. У звичайному браузері `GameGate` показує заглушку — окремого «сайту з грою» немає, є мініапс і CRM на `/admin`. Виняток — dev-режим (нижче), щоб можна було налагоджувати й ганяти `sim:e2e`.

### Авторизація

Мініапс шле в кожному запиті:

```
Authorization: tma <Telegram.WebApp.initData>
```

`initData` — підписаний телеграмом рядок. Сервер перевіряє підпис ботовим токеном:

```
secret = HMAC_SHA256(key="WebAppData", data=<bot_token>)
hash   = HMAC_SHA256(key=secret, data=<усі поля КРІМ hash, відсортовані, через \n>)
```

Викидається **тільки `hash`**. Поле `signature` (Ed25519, Bot API 8.0+) сучасні клієнти шлють разом із ним, і воно **входить** у те, що підписано ботовим токеном — доки його викидали, справжній initData із телеграма не проходив узагалі. Викидати `signature` треба в іншому методі: коли перевіряють не ботовим токеном, а публічним ключем телеграма. Обидва випадки (з полем і без) плюс його підміна покриті в `npm run test:auth`.

Це рахується **локально**, без жодного запиту до телеграма — тому падіння їхнього API не ламає вхід у гру. HMAC береться з рушія, нової залежності не знадобилось.

Гравець ідентифікується telegram id. Відкрив з іншого пристрою — той самий баланс; підмінив id у запиті — підпис не зійдеться. Перевірка покрита тестами (`npm run test:auth`): підміна `user.id`, чужий токен, протухлий і порожній `initData`, сміття замість хеша.

Додатково перевіряється **свіжість** `auth_date` (`INITDATA_MAX_AGE`, за замовчуванням доба) — інакше один раз перехоплений `initData` був би вічним ключем до акаунта.

### Dev-режим

Щоб гра відкривалась у звичайному браузері (і щоб ганявся `sim:e2e`), сервер приймає заголовок `x-dev-user: <число>` замість підпису. Вмикається, коли немає токена, або явно через `DEV_AUTH=true` — бо щойно токен з'являється для бота, браузер інакше почне отримувати 401.

Важливо, як саме він вмикається: **dev-режим не означає «пускати будь-кого»**. Якщо клієнт прислав `initData` і токен у нас є, підпис перевіряється по-справжньому, і підроблений отримає 401 навіть локально. На `x-dev-user` падаємо тільки коли заголовка `Authorization` немає зовсім.

Це не косметика: у першій версії гард дивився на `DEV_AUTH` раніше за заголовок, і підроблений `initData` мовчки ставав dev-гравцем — локальний прогін показував би зелене там, де в проді 401.

У продакшні гілка недосяжна за побудовою: `devAuth` завжди помножений на `!isProd`, а `NODE_ENV=production` без токена взагалі не дає серверу стартувати. Перевірено на живому сервері — у проді `x-dev-user` дає 401.

Згенерувати справжній підписаний `initData` для перевірки API руками:

```
npm run make:initdata -w @minedrop/engine -- <bot_token> [user_id]
```

### Що потрібно від тебе

| що | де взяти | обов'язково |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | @BotFather → `/newbot` | так, для прода |
| `WEBAPP_URL` | https-адреса фронта після деплою | так, інакше бот не зробить кнопку |
| `ADMIN_LOGIN` / `ADMIN_PASSWORD` | придумуєш сам | так, інакше в CRM неможливо увійти |
| `ADMIN_EMAIL` | пошта адміна | ні, лише для довідки в самій CRM |
| `MONGO_URL` | `docker compose up -d` локально | ні в dev (тоді все в пам'яті), так у проді |

Скопіюй [.env.example](.env.example) у `.env` і заповни. Решта має робочі значення. `.env` у git не потрапляє.

З `ADMIN_*` при старті засівається колекція `admins`: у базу лягає лише scrypt-хеш пароля з випадковою сіллю, сам пароль живе тільки в `.env`. Змінив `ADMIN_PASSWORD` — при наступному старті пароль перезапишеться, а активні сесії CRM скинуться. Порожній `ADMIN_PASSWORD` = адміна не заводити взагалі (пароля за замовчуванням у коді немає).

Телеграм **не відкриє** ні `http`, ні `localhost` — потрібен публічний домен з https. Для перевірки з телефона до деплою згодиться будь-який тунель (`cloudflared`, `ngrok`): підставляєш його адресу у `WEBAPP_URL`.

### Що вже зроблено під мініапс

- **Один origin.** Next проксює `/api/*` у Nest (`API_ORIGIN`). У вебв'ю телеграма запит на інший домен — це третя сторона з усіма її обмеженнями; тут цієї категорії проблем немає взагалі.
- **Свайпи.** `disableVerticalSwipes()` — без нього свайп по канвасу згортає мініапс і грати неможливо. Плюс вимкнено pull-to-refresh, зум подвійним тапом і виділення тексту.
- **Висота.** Верстка спирається на `--tg-viewport-stable-height`, а не на `100vh`: шторку можна тягнути, і при `100vh` низ інтерфейсу лишається за екраном.
- **Ідемпотентність ставки.** У вебв'ю мережа рветься регулярно. Клієнт шле `x-idempotency-key` і при обриві повторює запит **тим самим ключем** — сервер повертає вже зіграний раунд, а не списує ставку вдруге. Покрито в `sim:e2e`.
- **Бот не кладе API.** Мертвий токен або збій `api.telegram.org` під час деплою більше не валить сервер — бот логує помилку, гра працює далі. (Ловилось саме так: 401 від `deleteWebhook` клав увесь застосунок на старті.)
- **Тактильний відгук** на множниках і результаті раунду.
- **Старт без 14 МБ.** Див. нижче.

### Вага скінів

Зачаровані скіни (`_magic`) важать разом ~14 МБ — від 1.5 до 6.3 МБ кожен. Раніше вони блокували перший кадр: на мобільному інтернеті гравець пішов би раніше, ніж побачив рулетку.

Тепер блокуючий етап — тільки блоки й звичайні кірки (~40 КБ), а зачаровані вантажаться у фоні; якщо верстак трапився раніше, ніж вони доїхали, малюється звичайний скін.

**Але це прибрало затримку старту, а не трафік.** `lvl4_magic.gif` на 6.3 МБ — це повнорозмірний оригінал там, де потрібно ~256px. Файли варто перетиснути; скажи, коли можна їх чіпати.

### Деплой, коротко

1. Фронт і API — на одному домені (`API_ORIGIN` вказує на Nest).
2. `NODE_ENV=production`, `TELEGRAM_BOT_TOKEN`, `WEBAPP_URL` у змінних оточення.
3. @BotFather: `/newapp` або `/setmenubutton` з тією ж адресою.
4. Хочеш вебхук замість long polling — заповни `TELEGRAM_WEBHOOK_URL` і `TELEGRAM_WEBHOOK_SECRET`.

Long polling працює скрізь і нічого не потребує; вебхук потрібен, коли інстансів більше одного.

Стара версія (один `index.html`, без білду й сервера) лежить у [legacy/](legacy/) і досі відкривається подвійним кліком. Її [README](legacy/README.md) описує ту саму математику.

## Структура

```
packages/engine/     вся математика. Чиста, детермінована, без DOM і без мережі
  src/rng.ts         SHA-256 / HMAC / sfc32 + іменовані потоки випадковості
  src/config.ts      УСІ ЦИФРИ ГРИ: кірки, блоки, множники, рулетка, руда, фізика
  src/world.ts       нескінченна шахта, ряди сіються ПОРЯДКОВО, руда — покладами
  src/run.ts         фізика забігу: падіння, відскоки, розкол, HP, TNT, верстак, множники
  src/round.ts       повний раунд з одного сида: рулетка -> кірка -> політ -> виплата
  src/fairness.ts    commit-reveal
  sim/               симуляції та тести (нижче)

apps/api/            NestJS. Єдине місце, де рухаються гроші
  config/env.ts      усі змінні оточення з перевіркою на старті
  db/                ОДНЕ підключення до Mongo на весь застосунок
  common/rate-limit  лічильник частоти запитів (verify, вхід у CRM)
  telegram/          перевірка підпису initData + сам бот
  players/           баланс, pity-лічильники, nonce, сиди (Map + копія в Mongo)
  rounds/            POST /rounds/play — тут вирішується результат
  fairness/          публікація хеша, розкриття, публічна перевірка
  payments/          заявки на депозит, пул адрес, ЗІСТАВЛЕННЯ переказів
  watcher/           бот: читає мережі, згодовує перекази в payments
  withdrawals/       заявки на виведення (резерв балансу в момент заявки)
  admin/             CRM: обліковий запис адміна, сесії, гард, ендпоінти
  rates/             курс USDT/RUB для показу балансу в інших валютах

apps/web/            Next.js. HUD у React, поле у canvas
  src/game/          presenter (стани й камера), render, reel, assets
  src/components/    HUD, модалки (депозит, чесність, платежі)
  src/ui/            спільне для гри й CRM: Ask (свій confirm), NumField
  src/lib/api.ts     тонкий клієнт до API
  app/tokens.css     кольори, скруглення й тривалості — одні на все
  app/globals.css    стилі гри (тільки var(--…), жодного кольору)
  app/admin/         CRM: вхід + вкладки «Игроки / Заявки / Депозиты»
  public/            скіни, рамка рулетки, іконки валют

legacy/              вихідна vanilla-версія, працює як працювала
```

Фізика рахується **в клітинках, не в пікселях**, і крок симуляції **фіксований** (`SIM_DT = 1/120`). Тому гра однаково поводиться на будь-якому вікні й будь-якому фреймрейті, а `run.ts` ганяється в node без браузера.

### Стилі

Гра й CRM — один дизайн: плоскі поверхні, рамка 1px, скруглення 8–12px,
кольори тільки з [tokens.css](apps/web/app/tokens.css). Хардкод-кольору в
`globals.css` немає, і додавати його не треба — потрібного відтінку або
вже є токен, або його варто туди додати.

**Світла тема — тільки CRM.** Грі вона навмисно не робиться: під HUD лежить
намальована шахта, світлої версії тієї картинки не існує, і світлий інтерфейс
поверх темного канваса читався б гірше, а не краще. Гра ніде не ставить
`data-theme`, тому для неї завжди діє темний `:root`.

Нативних системних компонентів в інтерфейсі немає: `type="number"` замінює
[NumField](apps/web/src/ui/NumField.tsx), `confirm()`/`prompt()` —
[Ask](apps/web/src/ui/Ask.tsx), чекбокс — свій перемикач. Причина одна на всі:
браузер малює їх по-своєму, а частину (нативні діалоги) користувач може
вимкнути назавжди — і підтвердження мовчки перестане питати.

### Дані в Mongo

Одне підключення (`apps/api/src/db/mongo.service.ts`):

| колекція | `_id` | що лежить |
|---|---|---|
| `players` | telegram id | баланс, `dryStreaks` по ставках, сиди, nonce, останні 50 раундів |
| `payments` | uuid заявки | заявки на депозит: сума, курс, адреса, статус, хто його поставив |
| `deposit_addresses` | uuid адреси | пул адрес прийому + курсор спостерігача по кожній |
| `unmatched_payments` | uuid | перекази, що прийшли, але не зіставились із заявкою |
| `withdrawals` | uuid заявки | заявки на виведення |
| `settings` | назва розділу | що адмін міняє на ходу: режим прийому, мережі, монети |
| `admins` | uuid адміна | логін, пошта, **scrypt-хеш** пароля + сіль. Пароля в базі немає |

Порожній `MONGO_URL` — це dev-режим без БД: усе живе в пам'яті процесу й гине з рестартом. У проді сервер без бази не стартує.

### CRM `/admin`

Вхід за логіном і паролем адміна. Токен сесії лежить у `localStorage` і йде заголовком `Authorization: Bearer` — саме заголовком, а не кукою, тому CSRF-поверхні немає. Сесія живе `ADMIN_SESSION_TTL_H` годин (12 за замовчуванням) і не переживає рестарт API.

Три вкладки: **Игроки** (баланси, ручне поповнення, обнулення й видалення), **Заявки** (депозити, виведення, неопізнані перекази), **Депозиты** (слухач, режим, монети, мережі, адреси прийому).

> Раніше CRM була закрита лише перевіркою «не продакшн» — тобто в деві відкрита будь-кому, хто знає адресу. А `npm run tg` сам друкує `{публічний тунель}/admin` у консоль.

### Слухач переказів

Бот читає блокчейни й зараховує депозити сам. Живе в `apps/api/src/watcher/`.

**Один ключ на РОДИНУ мереж, а не на мережу.** У EVM однакова адреса й однакова подія переказу, тому один читач покриває шість мереж одним запитом — і гравець, який обрав Polygon, а надіслав у Base, грошей не втрачає.

| родина | провайдер | змінна | що покриває |
|---|---|---|---|
| EVM | Ankr Advanced API | `ANKR_KEY` | BNB Chain, Polygon, Base, Arbitrum, Optimism, Avalanche |
| TRON | TronGrid | `TRONGRID_KEY` | TRON (TRC20) |
| TON | TonAPI | `TONAPI_KEY` | TON (єдина мережа з коментарем до переказу) |
| Solana | Helius | `HELIUS_KEY` | Solana |

Родина без ключа просто не слухається, решта працює далі. Мережу в CRM при цьому увімкнути можна — просто зіставляти перекази доведеться руками.

**Два рубильники, і вони про різне.** «Слушатель» — чи бот узагалі ходить у мережу. Режим (`off / watch / semi / auto`) — наскільки йому дозволено чіпати гроші. Вимкнути слухача безпечно: прийом грошей від цього не зупиняється, гравці так само створюють заявки, просто зіставляє їх адмін.

**Рішень бот не приймає жодних.** Він тільки читає мережу й віддає знайдене в `PaymentsService.ingest()`. Яка це заявка, чи зараховувати, чи складати в неопізнані — вирішується там, і саме тому це вкрито тестами без жодного ключа (`npm run test:deposits`).

**Переказ зараховується у два кроки, а не в один.**

1. `ingest()` знаходить переказ і ставить заявку в **`processing`** («в обробці ботом»). Грошей не чіпає ніхто: індексатор бачить переказ, щойно той потрапив у блок, а блок ще може відкотитись.
2. Заявка лежить `finalitySec` своєї мережі, потім бот **перепитує мережу**, чи переказ на місці, і закриває її: `approved`/`rejected` із позначкою, хто це зробив — бот чи адмін.

Заявка в `processing` **не протухає**: тридцять хвилин відміряні на те, щоб людина встигла переказати. Вона встигла — далі чекає мережа, і карати за її повільність нема за що.

Поки заявка в `pending`, гравець може зняти її сам (`canceled`) — інакше помилка в сумі чи мережі коштувала б півгодини: друга заявка не створюється, доки висить перша. У `processing` скасування вже заборонене: переказ знайдено в мережі, і зняти заявку означало б викинути гроші, які вже пішли. Обидві межі закриті тестами в `npm run test:deposits`.

Перепитування має три відповіді, а не дві. `gone` — мережа прямо каже, що переказу немає (відкат блока), і тільки тоді бот відхиляє заявку сам. `unknown` — перепитати не вийшло (провайдер ліг): тоді віримо індексатору, який цей переказ і показав, бо підвішувати чужі гроші через власний збій зв'язку не можна.

Незіставлене складається в `unmatched_payments` **у будь-якому режимі**: заявка протухає за 30 хвилин, а гроші в мережі не протухають ніколи.

`npm run test:chains` перевіряє читачів: чисті функції — завжди, живі мережі — якщо в оточенні є ключі.

## Правила

| | |
|---|---|
| **Рулетка** | **Один** прокрут на ставку (0.62 с), як у класичному 777: потягнув — побачив результат. Кірка є в **16.7%** ставок (ваги кірок 20 проти `nothingWeight` 100). Розклад за ставку: Wooden 7.5% / Stone 4.2% / Iron 2.5% / Golden 1.7% / Diamond 0.83%. |
| **Гарантія (pity)** | `CONFIG.pity = 7` порожніх ставок поспіль → наступна **обов'язково** дає кірку (тір — за звичайними вагами). Лічильник **свій на кожен номінал ставки** (`PlayerRecord.dryStreaks`), тож набити промахи на 10 і зняти гарантію на 2000 не вийде. Прапорець потрапляє в `RoundResult.pity` — **без нього раунд не перевіряється**, див. Provably fair. |
| **Рівень кірки** | Дає **HP** (100 → 400) і **урон** (2 → 7). HP = скільки дотиків витримає, урон = як швидко довбає руду. На суму виграшу рівень **не** впливає. |
| **Розкол** | Земля / камінь / дерн / динаміт — міцність 1, падають з одного удару будь-якою кіркою. Міцність є тільки в руди: вугілля 2, залізо 4, лазурит і редстоун 5, золото 6, алмаз 9, ізумруд 10. |
| **Гроші** | Дерн, земля, камінь — **0** (це наповнювач). Вугілля 1 · залізо 5 · лазурит 10 · редстоун 15 · золото 20 · алмаз 45 · **ізумруд 130**. Ділиться на `payoutK`, множиться на ставку. |
| **Руда покладами** | Руда лягає не поклітинно, а суцільними жилами: шахта поділена на регіони по 6 рядів, і для кожного окремо вирішується, чи є в ньому поклад даного типу, де центр і скільки клітинок (`ORE_VEINS`). Що дорожча руда — то рідші й дрібніші поклади. |
| **TNT** | 9 променів із епіцентру, потужність гасне по дорозі — форма щоразу інша, органічна. Весь TNT у радіусі 2 детонує **гарантовано**, ланцюгом. Бонус за довжину ланцюга на весь виграш вибуху: 3 шт → ×1.10, 5 → ×1.25, 10 → ×1.50. Кірці шкоди **не** завдає (`cost: 0`), але підкидає. |
| **Верстак** | Прямий дотик: +1 рівень кірки і повне відновлення HP. На топ-тірі (Diamond) перший верстак лікує повністю, кожен наступний — лише +50 HP. Вибух TNT його просто ламає, без ефекту. Скін кірки **не** міняє. |
| **Стіл зачарування** | 3 фіксовані рівні множника **цієї кірки**: ×1.25 → ×1.5 → ×2.0, далі дотики без ефекту. Діє на весь подальший виграш кірки. Це **єдине**, що вмикає `_magic` скін. |
| **Блок-множник** | Не іксує вже зібране. Відкриває **вікно на 15 с**: усе, що зібрано за цей час, множиться на активний множник. Новий множник під час вікна — береться **більший** із двох (не перемножуються), таймер скидається. **x2 58% / x3 26% / x5 11% / x10 4% / x15 1%**. |
| **HP над кіркою** | Піксельне сердечко + «40/100». |
| **Історія** | Останні 12 ставок з іконкою і множником: колонка зліва на широкому екрані, компактна стрічка зверху на телефоні. |

> Бонусної гри більше немає. Її прибрано разом зі стріком і купівлею; `RoundMode` лишився типом з одним значенням `'bet'` як точка розширення. Якщо в коді чи коментарях трапиться згадка про бонуску — це залишок, а не механіка.

## Тести і баланс

```
npm run sim:smoke        # інваріанти фізики (тріщини, множники, стінки, NaN)
npm run sim:determinism  # ГОЛОВНИЙ: клієнтський прогін == серверний
npm run sim:fair         # commit-reveal відтворює раунд
npm run sim:e2e          # живий API: гаманець, pity, сиди, ідемпотентність
npm run test:auth        # перевірка підпису initData: усі способи підробки
npm run sim:final        # RTP + bootstrap CI + аналіз стелі
npm run sim:balance      # розбивка RTP по кірках і розподіл виплат
```

### `sim:determinism` — це не формальність

Уся конструкція «сервер вирішує, клієнт малює» тримається на тому, що з одного сида виходить один і той самий раунд. Тест ганяє кожен сид тричі: двічі серверним прогоном і раз «клієнтським» — з читанням рядів наперед (як робить рендер) і нерівними пачками кроків (як приходять кадри).

**Він одразу знайшов справжній баг.** Шахта прибирала ряди, що лишились позаду, від **найглибшої** кірки, а не від найвищої живої — і зрізала ряди, в яких ще копали. Ряд відновлювався з нуля: тріщини зникали, розбиті блоки поверталися цілими.

Полагоджено так, щоб помилитися вже не вийшло: прибиранням керує сам `Run`, межа рахується від **найвищої живої** кірки із запасом у 24 ряди, а `Mine.prune()` більше не можна кликати ззовні. З того самого боку прикрито й рендер: він читає шахту через `Mine.peek()`, який для викинутих рядів рахує їх **транзитно** і в кеш не кладе — тобто намальоване фізично не може стати станом гри.

### RTP

Заміряно на 120 000 послідовних ставок (`npm run sim:final -- 120000`), потік із живим pity-лічильником — саме так, як його веде сервер:

```
кірка (з pity): 21.78%  =  раз на 4.6 ставок
pity спрацював 7244 рази (6.0%), кірку дав у 7244 з 7244

payoutK у конфізі = 215   RTP при ньому: 95.56%
payoutK для рівно 95%    ≈ 216   (CI 92.85 .. 97.07%)

квантилі: 50% x0 | 90% x1.7 | 95% x5.8 | 99% x19 | 99.9% x37 | макс x102
стеля x500: жодного спрацювання на цій вибірці
```

Кірка випадає в 16.7% прокрутів, але з урахуванням гарантії кожної 8-ї порожньої ставки виходить 21.8% — саме ця цифра, а не 16.7%, і є частотою «щось сталося» для гравця.

> `sim/final.ts` рахує дві **різні** речі окремо: RTP при тому `K`, що реально стоїть у конфізі, і той `K`, який дав би рівно 95% на цій вибірці. Старий `sim/final.js` спочатку підбирав `K` під ціль, а потім друкував RTP із цим самим `K` — 95.0% виходило завжди, за побудовою, яким би не був `payoutK`.

### Стеля виграшу

`maxWinX = 500` — це **запобіжник, а не частина балансу**: на 120 000 ставок він не спрацював жодного разу (максимум склав x102 при p99.9 = x37). Хвіст тримають блок-множники: вікно на 15 с із множником до x15, накладене на зачарування до ×2.

Коли стеля таки спрацює, UI напише «СТЕЛЯ ВИГРАШУ x500» замість показаного множника — інакше гравець бачив би один множник, а виплату за іншим, і читав це як обман.

Оцінка RTP лишається шумною: розподіл виграшу має важкий хвіст, тому одна цифра без інтервалу нічого не варта — `sim/final.ts` рахує bootstrap-CI (на 120k це ще ±2 п.п.). Хочеш точніше — став більше ставок: `npm run sim:final -w @minedrop/engine -- 500000`.

## Що лишилось зробити

Це чесний список, а не приховані TODO в коді:

- **Ліміт на `POST /rounds/play`.** Ідемпотентний ключ рятує від дублів того самого запиту, але не від навмисного флуду. Ліміт частоти вже є на `POST /fairness/verify` і на вхід у CRM (`apps/api/src/common/rate-limit.ts`) — той самий `RateLimiter` треба повісити й на гру, per-гравець.
- **Журнал операцій.** Ставки й поповнення міняють баланс, але окремої історії рухів грошей немає: є `PlayerRecord.history` (останні 50 раундів) і колекція `payments`. Ручні поповнення адміна ніде, крім логу, не лишаються.
- **Сесії CRM живуть у пам'яті процесу.** Рестарт API = повторний вхід. Це навмисно (токен нікуди не витікає), але якщо колись стане незручно — виносити в БД разом із TTL.
- **Перетиснути скіни** — зачаровані кірки важать разом ~14 МБ, від 1.5 до 6.3 МБ кожна. Вантажаться у фоні (гру не блокують), але трафік це не прибирає: 6.3 МБ на одну анімацію там, де треба ~256 px.
- **Ручне прицілювання** (`manualAim` зі старої версії) прибрано: колонку тепер обирає сервер. Щоб повернути, колонку треба слати в запиті **до** розіграшу, інакше клієнт знову почне впливати на результат.
- **Іконки монет і мереж.** `DepositModal` просить `/tokens/{usdt,usdc}.png` і `/networks/{id}.png` на кожну з дев'яти мереж. Файлів немає — `Icon` мовчки ховається, вікно працює без них, але виглядає голо. Перелік — у розділі «Скіни».
- **Обнулення й видалення гравця в CRM — тимчасові.** Зроблені, щоб розгрібати наслідки тестів руками. Журналу вони по собі не лишають, крім рядка в логу сервера.
