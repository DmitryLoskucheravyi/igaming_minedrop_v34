# Minedrop

Одна ставка = до **7 спроб** на вертикальній рулетці (виглядає як класичний однобарабанний слот 777: одна стрічка символів, у вікні видно три — над, на лінії виплати і під). З кожної спроби випадає або **кірка**, або **пусто** (Х). **Перша ж кірка зупиняє прокрути** — рулетка їде вгору, поле піднімається, і кірка летить у нескінченну шахту на 10 колонок. Не випало за всі 7 — ставка згоріла.

Кірка б'є блоки, **відскакує й перевертається** (тому летить по діагоналі). Земля, камінь і динаміт падають з одного удару; **руда розколюється поступово** — тріщини наростають, як у майні. Політ триває, **поки не скінчиться HP**.

## Що змінилось: результат тепер рахує сервер

Раніше вся гра жила в браузері: `Math.random()` вирішував, що випало, і той самий код нараховував виграш. Це нормально для прототипу і неприпустимо далі — відкрив консоль, підмінив `Game.balance`, і все.

Тепер архітектура така, як і має бути:

```
БРАУЗЕР                        СЕРВЕР (NestJS)
   │
   │  POST /rounds/play  { bet, mode }
   ├──────────────────────────────────►
   │                              1. перевірив ставку й режим
   │                              2. списав вартість
   │                              3. nonce += 1, узяв сид
   │                              4. ПРОГРАВ раунд у рушії до кінця
   │                              5. нарахував виплату, оновив стрік
   │  { seed, spins, tiers, payout, balanceAfter, ... }
   ◄──────────────────────────────────┤
   │
   ├─ createRun(seed) ──► той самий рушій відтворює політ
   │                      кадр за кадром, для картинки
   │
   └─ у кінці звіряє свою суму з серверною ──► «✓ перевірено»
```

Клієнт **не вирішує нічого**. Політ по мережі не передається — він відтворюється з сида тим самим кодом. Наприкінці забігу клієнт перераховує виплату сам і показує в HUD, зійшлося чи ні. Розбіжність — це баг детермінізму, і його видно одразу, а не через місяць у звітах.

### Provably fair

Не гасло, а робочі кнопки в панелі «ЧЕСНІСТЬ»:

1. Сервер публікує `sha256(serverSeed)` **до** гри — змінити сид заднім числом уже не вийде.
2. Гравець задає свій `clientSeed` — сервер не може підібрати сид під конкретну людину.
3. Сид раунду = `HMAC-SHA256(serverSeed, "clientSeed:nonce")`, `nonce` росте на кожному раунді.
4. Кнопка «розкрити» закриває серію і показує `serverSeed`. Після цього **будь-який** раунд серії перераховується прямо в браузері — `resolveRound()` там той самий, що й на бекенді.

SHA-256 і HMAC написані в рушії руками (~90 рядків, без залежностей) саме тому, що мають однаково працювати в node і в браузері: `node:crypto` у браузері немає, а WebCrypto асинхронний.

## Запуск

`npm install` роблять **тільки з кореня** — це npm workspaces, `node_modules` один на все репо, а `@minedrop/engine` лінкується в застосунки симлінком. `npm install` усередині `apps/web` створить окремий `node_modules` і зламає цей лінк.

```
npm install
npm run dev          # збирає рушій, потім піднімає API :4000 і веб :3000
```

Окремо:

```
npm run dev:api      # NestJS на :4000
npm run dev:web      # Next.js на :3000
npm run build        # рушій -> api -> web
npm run typecheck
```

Локально нічого налаштовувати не треба: без `TELEGRAM_BOT_TOKEN` сервер вмикає dev-авторизацію і гра відкривається у звичайному браузері.

> `npm audit fix --force` **не запускати** — він тягне мажорний Next 16. Вразливості `postcss` закриті точковим `overrides` у кореневому `package.json`. Через це `npm ls postcss` пише `invalid` (Next пінить стару версію) — так і має бути.

## Телеграм-мініапс

Гра працює і як звичайний сайт, і як Mini App. Різниця тільки в тому, **чим підтверджується особа гравця**.

### Авторизація

Мініапс шле в кожному запиті:

```
Authorization: tma <Telegram.WebApp.initData>
```

`initData` — підписаний телеграмом рядок. Сервер перевіряє підпис ботовим токеном:

```
secret = HMAC_SHA256(key="WebAppData", data=<bot_token>)
hash   = HMAC_SHA256(key=secret, data=<поля без hash і signature, відсортовані, через \n>)
```

Це рахується **локально**, без жодного запиту до телеграма — тому падіння їхнього API не ламає вхід у гру. HMAC береться з рушія, нової залежності не знадобилось.

Гравець ідентифікується telegram id. Відкрив з іншого пристрою — той самий баланс; підмінив id у запиті — підпис не зійдеться. Перевірка покрита тестами (`npm run test:auth`): підміна `user.id`, чужий токен, протухлий і порожній `initData`, сміття замість хеша.

Додатково перевіряється **свіжість** `auth_date` (`INITDATA_MAX_AGE`, за замовчуванням доба) — інакше один раз перехоплений `initData` був би вічним ключем до акаунта.

### Dev-режим

Щоб гра відкривалась у звичайному браузері (і щоб ганявся `sim:e2e`), сервер приймає заголовок `x-dev-user: <число>` замість підпису. Вмикається, коли немає токена, або явно через `DEV_AUTH=true` — бо щойно токен з'являється для бота, браузер інакше почне отримувати 401.

Важливо, як саме він вмикається: **dev-режим не означає «пускати будь-кого»**. Якщо клієнт прислав `initData` і токен у нас є, підпис перевіряється по-справжньому, і підроблений отримає 401 навіть локально. На `x-dev-user` падаємо тільки коли заголовка `Authorization` немає зовсім.

Це не косметика: у першій версії гард дивився на `DEV_AUTH` раніше за заголовок, і підроблений `initData` мовчки ставав dev-гравцем — локальний прогін показував би зелене там, де в проді 401.

У продакшні гілка недосяжна за побудовою: `devAuth` завжди помножений на `!isProd`, а `NODE_ENV=production` без токена взагалі не дає серверу стартувати. Перевірено на живому сервері — у проді `x-dev-user` дає 401.

Згенерувати справжній підписаний `initData` для перевірки API руками:

```
npm run make:initdata -w @minedrop/engine -- <bot_token> [user_id]
```

### Що потрібно від тебе

| що | де взяти | обов'язково |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | @BotFather → `/newbot` | так, для прода |
| `WEBAPP_URL` | https-адреса фронта після деплою | так, інакше бот не зробить кнопку |

Скопіюй [.env.example](.env.example) у `.env` і заповни ці два рядки. Решта має робочі значення. `.env` у git не потрапляє.

Телеграм **не відкриє** ні `http`, ні `localhost` — потрібен публічний домен з https. Для перевірки з телефона до деплою згодиться будь-який тунель (`cloudflared`, `ngrok`): підставляєш його адресу у `WEBAPP_URL`.

### Що вже зроблено під мініапс

- **Один origin.** Next проксює `/api/*` у Nest (`API_ORIGIN`). У вебв'ю телеграма запит на інший домен — це третя сторона з усіма її обмеженнями; тут цієї категорії проблем немає взагалі.
- **Свайпи.** `disableVerticalSwipes()` — без нього свайп по канвасу згортає мініапс і грати неможливо. Плюс вимкнено pull-to-refresh, зум подвійним тапом і виділення тексту.
- **Висота.** Верстка спирається на `--tg-viewport-stable-height`, а не на `100vh`: шторку можна тягнути, і при `100vh` низ інтерфейсу лишається за екраном.
- **Ідемпотентність ставки.** У вебв'ю мережа рветься регулярно. Клієнт шле `x-idempotency-key` і при обриві повторює запит **тим самим ключем** — сервер повертає вже зіграний раунд, а не списує ставку вдруге. Покрито в `sim:e2e`.
- **Бот не кладе API.** Мертвий токен або збій `api.telegram.org` під час деплою більше не валить сервер — бот логує помилку, гра працює далі. (Ловилось саме так: 401 від `deleteWebhook` клав увесь застосунок на старті.)
- **Тактильний відгук** на множниках і результаті раунду.
- **Старт без 14 МБ.** Див. нижче.

### Вага скінів

Зачаровані скіни (`_magic`) важать разом ~14 МБ — від 1.5 до 6.3 МБ кожен. Раніше вони блокували перший кадр: на мобільному інтернеті гравець пішов би раніше, ніж побачив рулетку.

Тепер блокуючий етап — тільки блоки й звичайні кірки (~40 КБ), а зачаровані вантажаться у фоні; якщо верстак трапився раніше, ніж вони доїхали, малюється звичайний скін.

**Але це прибрало затримку старту, а не трафік.** `lvl4_magic.gif` на 6.3 МБ — це повнорозмірний оригінал там, де потрібно ~256px. Файли варто перетиснути; скажи, коли можна їх чіпати.

### Деплой, коротко

1. Фронт і API — на одному домені (`API_ORIGIN` вказує на Nest).
2. `NODE_ENV=production`, `TELEGRAM_BOT_TOKEN`, `WEBAPP_URL` у змінних оточення.
3. @BotFather: `/newapp` або `/setmenubutton` з тією ж адресою.
4. Хочеш вебхук замість long polling — заповни `TELEGRAM_WEBHOOK_URL` і `TELEGRAM_WEBHOOK_SECRET`.

Long polling працює скрізь і нічого не потребує; вебхук потрібен, коли інстансів більше одного.

Стара версія (один `index.html`, без білду й сервера) лежить у [legacy/](legacy/) і досі відкривається подвійним кліком. Її [README](legacy/README.md) описує ту саму математику.

## Структура

```
packages/engine/     вся математика. Чиста, детермінована, без DOM і без мережі
  src/rng.ts         SHA-256 / HMAC / sfc32 + іменовані потоки випадковості
  src/config.ts      УСІ ЦИФРИ ГРИ: кірки, блоки, множники, рулетка, бонуска, фізика
  src/world.ts       нескінченна шахта, ряди сіються ПОРЯДКОВО
  src/run.ts         фізика забігу: падіння, відскоки, розкол, HP, TNT, верстак, множники
  src/round.ts       повний раунд з одного сида: рулетка -> кірки -> політ -> виплата
  src/fairness.ts    commit-reveal
  sim/               симуляції та тести (нижче)

apps/api/            NestJS. Єдине місце, де рухаються гроші
  players/           баланс, стрік, nonce, сиди (in-memory — заглушка під БД)
  fairness/          публікація хеша, розкриття, публічна перевірка
  rounds/            POST /rounds/play — тут вирішується результат

apps/web/            Next.js. HUD у React, поле у canvas
  src/game/          presenter (стани й камера), render, reel, assets
  src/components/    HUD і панель чесності
  src/lib/api.ts     тонкий клієнт до API
  public/assets/     скіни

legacy/              вихідна vanilla-версія, працює як працювала
```

Фізика рахується **в клітинках, не в пікселях**, і крок симуляції **фіксований** (`SIM_DT = 1/120`). Тому гра однаково поводиться на будь-якому вікні й будь-якому фреймрейті, а `run.ts` ганяється в node без браузера.

## Правила

| | |
|---|---|
| **Рулетка** | До 7 спроб по 0.62с. Шанс кірки ~16% за спробу → кірка є в ~71% ставок. |
| **Рівень кірки** | Дає **HP** (100 → 400) і **урон** (1 → 7). HP = скільки ударів витримає, урон = як швидко довбає руду. На суму виграшу рівень **не** впливає. |
| **Розкол** | Блок має міцність. Земля/камінь/динаміт — 1, вугілля 2, залізо 4, золото 6, алмаз 9. Кірка знімає свій урон за удар. Мідна (урон 1) довбає алмаз 9 разів, алмазна (урон 7) — двічі. |
| **HP над кіркою** | Піксельне сердечко + «40/100». |
| **Гроші** | Земля +2, камінь +4, вугілля +8, залізо +16, золото +30, алмаз +60. Ділиться на `payoutK`, множиться на ставку. |
| **TNT** | Хаотичний вибух: із твердих блоків у сусідній клітинці (до 8 кандидатів) випадково розносить від **3 до 6** — не завжди весь квадрат. Сам коштує 20 HP і підкидає кірку. |
| **Верстак** | +1 рівень кірки і повне відновлення HP. Вмикається `_magic` скін. |
| **Х-блоки** | Множать **уже накопичений** виграш. Зароблене після них цим множником не іксується — тільки наступними. **x2 58% / x3 26% / x5 11% / x10 4% / x15 1%** (E = 3.04). Трапляються і в звичайній шахті, і в бонусній. |
| **Історія** | Колонка зліва: останні 12 ставок з іконкою і множником. |

### Бонусна гра

Рулетка сама крутить **15 разів**, і скільки кірок випало — стільки й **падає в шахту одночасно**, у спільний рахунок. У бонусній рулетці «пусто» важить менше і кірки зміщені до вищих рівнів — виходить **~11 кірок** за бонуску.

Щільність Х-блоків у бонусній шахті майже така сама, як у звичайній (`multWeight` 0.3 проти `multWeightBase` 0.25). Різниця в кількості спійманих множників (1.5 проти 0.13 за забіг) береться не зі щільності, а з того, що копає 11 кірок замість однієї.

Два способи потрапити:
- **Стрік** — кірка випала N ставок підряд. Стрік лічить **сервер** і тільки по звичайних ставках; бонусні раунди його не подовжують і не обнуляють.
- **Купити** — за `bonus.buyCost` ставок (зараз x70).

> ⚠️ **Стрік = 12, а не 3.** Кірка є в ~71% ставок, тому «3 підряд» спрацьовує **раз на 6 ставок**, і бонуска ціною x70 давала б RTP понад 1000%. При 12 вона спрацьовує раз на ~210 ставок і все сходиться.
> Хочеш саме 3 — тоді одне з двох, обидва в один рядок конфіга:
> - `bonus.buyCost: 6` — бонуска стає дешевою і слабкою;
> - `nothingWeight: 580` — кірка випадає в ~17% ставок замість 71%.

## Тести і баланс

```
npm run sim:smoke        # інваріанти фізики (тріщини, множники, стінки, NaN)
npm run sim:determinism  # ГОЛОВНИЙ: клієнтський прогін == серверний
npm run sim:fair         # commit-reveal відтворює раунд
npm run sim:e2e          # живий API: гаманець, стрік, сиди, ідемпотентність
npm run test:auth        # перевірка підпису initData: усі способи підробки
npm run sim:final        # RTP + bootstrap CI + аналіз стелі
npm run sim:balance      # розбивка RTP по кірках і розподіл виплат
```

### `sim:determinism` — це не формальність

Уся конструкція «сервер вирішує, клієнт малює» тримається на тому, що з одного сида виходить один і той самий раунд. Тест ганяє кожен сид тричі: двічі серверним прогоном і раз «клієнтським» — з читанням рядів наперед (як робить рендер) і нерівними пачками кроків (як приходять кадри).

**Він одразу знайшов справжній баг.** Шахта прибирала ряди, що лишились позаду, від **найглибшої** кірки. У звичайній грі кірка одна, і це працювало. У бонусці їх 11, вони розтягуються на сотні рядів — і прибирання зрізало ряди, в яких відсталі ще копали. Ряд відновлювався з нуля: тріщини зникали, розбиті блоки поверталися цілими.

У legacy цей баг теж є (`game.js` прибирав від камери), просто там не було з ким розійтися — гра сама себе й рахувала.

Полагоджено так, щоб помилитися вже не вийшло: прибиранням керує сам `Run`, межа рахується від **найвищої живої** кірки із запасом у 24 ряди, а `Mine.prune()` більше не можна кликати ззовні.

### RTP: цифру треба перевірити

Поточні заміри (40 000 ставок + 15 000 бонусок, `payoutK = 610`, поле 10 колонок, TNT 3–6 блоків):

```
RTP разом 92.9%   (звичайна гра 60.6%, бонуски за стрік 32.3%)
E[бонуска] = x67.8 (95% CI: x63.8 .. x72.1)
кірка в 70.9% ставок | стрік 12 спрацьовує раз на 210 ставок
щоб RTP був рівно 95%, на цій вибірці треба payoutK = 596
```

> ⚠️ **У старому README стояло «RTP разом 95.0%», і ця цифра була тавтологічною.** Старий `sim/final.js` спочатку **підбирав** `K` під ціль 95%, а потім друкував RTP, порахований із цим самим `K` — тобто 95.0% виходило завжди, за побудовою, яким би не був `payoutK` у конфізі. `sim/final.ts` рахує дві різні речі окремо: RTP при тому `K`, що реально стоїть у конфізі, і той `K`, який дав би рівно 95% на цій вибірці.
>
> **Поле стало ширшим (8 → 10 колонок), а TNT почав розносити випадково 3–6 блоків замість фіксованого квадрата** — обидві зміни зменшують середню кількість очок за забіг, тому RTP при незмінному `payoutK = 610` просів із 97.7% до 92.9%. Це не похибка виміру, а прямий наслідок ігрових правок; довірчий інтервал у межах ~±5 п.п. на цій вибірці.
>
> **`payoutK` я не чіпав** — це продуктове рішення, не рефакторинг. Хочеш повернути RTP ближче до 95% — постав `payoutK: 596` у `packages/engine/src/config.ts`, але спершу прогони `npm run sim:final -w @minedrop/engine -- 200000 80000`, бо на 15 000 бонусок оцінка ще гуляє на кілька відсотків.

### Стеля виграшу — важливе застереження

`maxWinX = 5000` спрацьовує раз на ~880 бонусок (0.11%), але **зрізає 22% віддачі бонуски = 9.1 п.п. загального RTP**. Тобто стеля — не запобіжник, а несуча конструкція балансу: 0.1% подій тримають ~9% RTP.

Наслідки, про які треба знати:
- **Оцінка RTP крихка.** E[бонуска] має важкий хвіст, тому одна цифра нічого не варта — `sim/final.ts` рахує bootstrap-CI. На 15 000 бонусок інтервал ще ±14%.
- **Прибирання x25/x100 хвіст майже не вкоротило.** Хвіст будує **кількість** множників, а не їхній розмір: при `multWeight = 1.0` кеп зрізав 85% віддачі. Саме тому `multWeight` тримається на 0.3.
- Якщо треба, щоб стеля стала справжнім запобіжником — правильний хід не крутити `maxWinX`, а обмежити сам ланцюг (`Run.multChain`) явним максимумом. Це зробить хвіст обмеженим за побудовою, а не зрізаним постфактум.

Коли стеля спрацьовує, UI пише «СТЕЛЯ ВИГРАШУ x5000» замість показаного множника — інакше гравець бачив би `X3000` і виплату x5000 і читав це як обман.

## Що лишилось зробити

Це чесний список, а не приховані TODO в коді:

- **Сховище.** `PlayersService` тримає гравців у `Map`, ключ — telegram id. Перезапустив процес — баланси обнулились. Це єдине, що по-справжньому блокує запуск на людях. Під продакшн міняється один файл: методи вже написані як «знайти → змінити → зберегти», а списання й нарахування зроблені однією операцією, щоб лягли в транзакцію.
- **Тестове поповнення балансу.** Поки нема ні реальних грошей, ні адмінки, `findOrCreate()` сам повертає баланс до `CONFIG.startBalance`, якщо він упав нижче найдешевшої ставки — спрацьовує на будь-якому зверненні (рефреш аппки, новий раунд). Зручно для тестів, але це **не** механіка гри — прибрати разом зі справжнім сховищем і справжнім поповненням.
- **Нарахування балансу.** Домовились, що це робить адмін вручну; адмінки поки немає. Коли знадобиться — це ендпоінт із окремим ключем і запис у той самий журнал операцій, що й ставки.
- **Ліміти запитів.** `POST /rounds/play` нічим не обмежений. Ідемпотентність рятує від дублів того самого запиту, але не від навмисного флуду — потрібен rate-limit на гравця.
- **Перетиснути скіни** — 14 МБ трафіку, див. вище.
- **Ручне прицілювання** (`manualAim` зі старої версії) прибрано: колонку тепер обирає сервер. Щоб повернути, колонку треба слати в запиті **до** розіграшу, інакше клієнт знову почне впливати на результат.
